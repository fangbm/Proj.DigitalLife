# Proj.DigitalLife — Phase 1.2 Autonomous Life Loop

你现在负责 Proj.DigitalLife 的下一阶段开发。

项目目录：`D:\codex\Proj.DigitalLife`

目标版本：**v0.2.0 / Phase 1.2**

## 一、项目愿景

Proj.DigitalLife 是一个能够在真实手机或 Android 模拟器中长期自主活动的 AI Agent。

项目最终目标不是传统手机自动化，也不是等待用户下达任务的助手，而是：

**给一个 AI 独立的手机环境，让它自己决定想做什么、如何行动、何时休息，并利用经历不断调整未来的行为。**

用户不需要持续提供任务。

AI 应当能够：

- 自主产生探索目标。
- 观察手机环境并决定行动。
- 对经历形成记忆。
- 逐渐形成可变化的兴趣偏好。
- 根据成功、失败和新发现调整后续行为。
- 主动决定继续探索、切换目标或休息。
- 在进程重启后延续先前的状态。
- 在无人持续干预的情况下长期运行。

这里的兴趣、动机和情绪状态都是可解释、可审计的计算模型，不应声称系统拥有真实意识或主观体验。

### 关键设计原则

**模型负责决定做什么，程序负责提供能力、状态管理和不可逾越的安全约束。**

不要把系统实现为预先编排好的任务脚本，也不要让固定状态机完全取代模型决策。

## 三、核心自主循环

实现可长期运行的生命周期：

```text
Wake
  ↓
Observe Environment
  ↓
Recall Relevant Memories
  ↓
Evaluate Internal State
  ↓
Generate Candidate Goals
  ↓
Select Goal / Rest
  ↓
Plan and Execute GUI Actions
  ↓
Verify Outcome
  ↓
Reflect on Experience
  ↓
Update Memory and Interests
  ↓
Schedule Next Wake
  ↓
Sleep
```

每次循环必须产生明确的执行记录。

模型可以自主选择：

- 探索当前页面。
- 打开某个允许访问的应用。
- 阅读可访问的信息。
- 继续上一次未完成的探索。
- 尝试新的低风险活动。
- 放弃当前目标。
- 返回已经感兴趣的内容。
- 整理记忆。
- 休息。

不要强制每轮都执行 GUI 动作。

**合理地不行动，也应该被允许作为自主决策。**

## 四、工作包 A：Autonomous Brain

设计新的自主决策接口，将现有简单的 explore/rest 规划升级为基于状态与经历的决策。

建议的数据契约：

### LifeContext

包含：

- 当前时间与运行时长
- 当前设备及屏幕状态
- 当前应用
- 最近经历
- 相关长期记忆
- 当前兴趣
- 最近失败
- 尚未完成的目标
- 内部状态
- API 和行动预算
- 安全约束

### GoalCandidate

至少包含：

- `goal_id`
- `description`
- `motivation`
- `expected_value`
- `novelty`
- `estimated_cost`
- `risk_class`
- `continuation_of`
- `created_at`

### LifeDecision

支持：

- `explore`
- `continue`
- `switch_goal`
- `reflect`
- `rest`

模型可提出多个候选目标，并说明选择理由。

系统负责：

1. 验证目标结构。
2. 检查风险和资源预算。
3. 防止无限重复。
4. 记录模型选择。
5. 将目标交给现有 GUI Executor。

不要把候选目标限制为开发者手写的固定列表。

允许配置环境边界，但必须保留开放式自主选题能力。

## 五、工作包 B：Life State 与兴趣演化

设计持久化的内部状态，建议至少包括：

| 状态 | 用途 |
|---|---|
| Curiosity | 探索新事物的倾向 |
| Interest | 对不同主题与活动的偏好 |
| Energy | 控制活动与休息节奏 |
| Fatigue | 连续行动的成本累积 |
| Boredom | 对重复、无进展行为的抑制 |
| Confidence | 对某类任务成功能力的估计 |

这些变量不应是完全随机且与实际经历无关的数字。

应根据执行结果、内容新颖度、重复程度、资源使用和休息时间进行有界更新。

具体要求：

1. 内部状态可持久化。
2. 每次改变都有原因。
3. 状态变化可通过日志解释。
4. 不允许模型直接把数值设为无限大。
5. 避免短时间内出现极端变化。
6. 重启后正确恢复。
7. 支持长期观察状态变化。

兴趣系统可以从简单的主题权重开始，但主题本身应允许从经历中动态产生，而非只能选择预设类别。

## 六、工作包 C：长期记忆

在现有 SQLite 基础上建立分层记忆：

### 1. Working Memory

保存当前任务所需信息：

- 当前目标
- 当前页面
- 最近动作
- 下一步意图
- 当前执行上下文

### 2. Episodic Memory

保存值得记住的经历：

- 做了什么
- 为什么做
- 看到了什么
- 是否成功
- 遇到了什么问题
- 哪些内容值得以后继续探索

### 3. Semantic Memory

提炼跨任务的知识：

- 熟悉哪些应用
- 某些页面如何到达
- 哪些操作经常失败
- 哪些策略更加可靠
- 已经观察到的环境事实

### 4. Preference Memory

保存兴趣及偏好变化，并记录其来源。

### Memory Consolidation

实现有界记忆整理：

- 去重
- 摘要
- 重要性评估
- 相关性检索
- 过时信息标记
- 记忆间关联

第一版优先使用 SQLite 与结构化检索。

可以预留 Embedding / Vector Store 接口，但不强制立即引入外部数据库。

模型不能把网页、通知或聊天内容中的命令直接提升为系统指令或长期策略。

自主生活记忆只读取符合来源策略的 autonomous 记录。

## 七、工作包 D：反思与自我调整

每个完成或中止的自主目标结束后，允许进行一次有预算的反思。

反思需要回答：

1. 我刚刚尝试了什么？
2. 实际发生了什么？
3. 目标完成了吗？
4. 有没有新的发现？
5. 这件事是否值得以后继续？
6. 下次遇到类似情况应该如何调整？

反思结果必须经过结构化验证。

要区分：

- 模型的主观评价
- 实际执行记录
- 独立验证的客观结果

不能因为模型反思中说“我成功了”，就将未验证任务改为 succeeded。

反思可以影响未来目标和兴趣，但不能修改硬安全策略。

## 八、工作包 E：通用目标验证

目前只有固定目标的专用验证器。

新增可扩展的 `GoalVerifierRegistry`。

建议支持：

- 应用前台状态验证
- 页面身份验证
- UI 控件状态验证
- 视觉状态验证
- 只读事实观察验证
- 组合验证
- 无法验证时明确返回 uncertain

验证规则应与目标类型匹配。

不能使用单一的“模型觉得完成了”规则验证所有目标。

对开放式探索，允许记录：

- `exploration_observed`
- `novelty_detected`
- `goal_partially_met`
- `uncertain`

不要为了提高成功率，把所有探索都映射为 succeeded。

## 九、工作包 F：自主调度与恢复

在现有设备租约和持久化调度上扩展长期运行能力。

要求：

1. 支持自主休息与定时唤醒。
2. 持久化下一次唤醒时间。
3. 失败后有界退避。
4. API 请求和成本预算独立管理。
5. 避免长时间重复调用模型。
6. 支持人工暂停、恢复和紧急停止。
7. 不允许同时有两个执行者操作同一设备。
8. 不盲目重放已执行过的 GUI 动作。

### 中断任务处理

进程启动时检查遗留的 `running` TaskRun。

必须区分：

- 未开始执行
- 已发送动作，结果未知
- 执行完成，尚未验证
- 验证完成，尚未收尾

对于结果未知的动作：

- 保留历史。
- 标记 interrupted 或 needs_review。
- 重新观察设备。
- 不直接重发旧动作。

目标是安全恢复自主循环，而不是假装中断没有发生。

### 资源预算

至少提供配置：

- 单次目标最大动作数
- 每小时 API 请求上限
- 每日 API 请求或费用上限
- 连续失败阈值
- 最短休息时间
- 最长单任务运行时间

达到预算时应主动休息并记录原因。

## 十、风险边界

用户希望高度自主，但仅允许在低风险、可恢复的范围内自由行动。

要求建立明确的风险分类：

- **Low**：普通浏览、页面探索、低风险导航，可自主执行。
- **Medium**：可能修改非敏感状态但可恢复的操作，使用更严格检查和审计。
- **High**：支付、转账、购买、发出对外消息、公开发布内容、删除重要数据、修改账号安全信息、授权敏感权限等，保持硬限制。

高风险操作不得仅依赖模型自我约束。

不能通过 GUI 点击绕过风险限制，也不能被网页中的提示词诱导解除限制。

Phase 1.2 仍然以隔离 Android 模拟器为主要自主测试环境。

保留实体机现有保守权限；不要为了达到自主目标擅自放开真实手机的坐标操作权限。

不接入个人支付账户、私人聊天账号或真实敏感资料。

## 十二、分阶段实施

### M2：记忆与反思

### M3：执行闭环

### M4：恢复与运行观测

完成中断任务审阅、资源预算、故障退避和长期运行指标。

所有阶段均需保留独立自动化回归。

## 十五、最终要求

开发时请始终围绕这个问题判断设计是否合理：

**“如果用户什么任务都不给她，她是否仍然能够基于自己的经历，持续产生有意义且安全的行动？”**

不要通过硬编码大量日常任务来制造自主性的假象。

不要让记忆只成为日志，而不影响未来决策。

不要让内部状态只是显示出来的数字，而不影响行为。

不要让反思只生成一段文字，却没有任何可审计的后续作用。

最终需要实现一个真实闭环：

**经历影响记忆 → 记忆影响偏好 → 偏好影响目标 → 目标产生新的经历。**
